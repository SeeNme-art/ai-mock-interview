# 02 · 面试业务规则

> v2.0 · 目标设计。依据 D02、D06–D15；本文件定义产品行为，字段和接口以 [04](04-数据与接口契约.md) 为准。

## 1. 材料与确认

三种入口汇聚到同一画像：示例、填写/粘贴、文件上传。画像只保留出题所需的技能、项目、经验信息，不因未提供学历或年限而编默认内容；姓名可统一显示“候选人”。学历不作为技术能力评分依据。

项目允许课程作业、毕业设计和自学练习。最少需要能说明“做过什么”；背景、结果、量化数字允许缺失。缺项可成为澄清方向，但不能要求用户编造。完全无项目时由用户确认进入 `knowledge_only`，不凭技能词虚构经历。

流程：基础清理 → 提取 → 字段来源校验 → 可编辑确认 → 基础敏感信息检测 → 保存已确认画像。基础检测不保证穷举所有个人信息，文本字段白名单也不能保证零漏检。

抽取校验工程规则：

- 空值标 `missing`，必须先判空，不能利用空字符串是任意文本子串而标 `exact`。
- `exact` 是规范化后有原文定位，`review_required` 是存在差异需人工确认，`unlocated` 是不能定位，`edited` 是用户主动编辑，`provided` 是直接填写/示例。原始模型提取状态和最终字段来源分别记录。
- 数字、单位、否定词、技术名称与项目归属单独提示；不能仅以 80% 字符重合将数字错误当成无害调整。
- 原文定位是文本出处证据，不证明经历真实；跨项目归属仍需用户核对。
- 失败字段不伪造补齐，可进行一次受统一预算限制的重试；仍失败留空或引导编辑。错误阈值按实际必需信息判定，不因“两个可选字段失败”一律丢弃整份材料。
- 提取评测的分母包含人工标注应提取而遗漏的字段，不能只数模型输出字段。

项目摘录需要保住选型、原因与指标等细节，但长度有上限且经过用户确认。原始文本只供临时预览定位，不进入长期业务表。用户编辑后保留已确认字段，不再长期保存被替换的未确认文字。

## 2. 规划与出题

### 2.1 两个独立维度

| 维度 | 取值 | 用途 |
|---|---|---|
| `task_type` | `knowledge` / `project` | 选择适用评分规则 |
| `generation_method` | `original` / `rewrite` / `generated` | 说明题面怎么产生 |

知识题必须绑定审核题目和要点；可以直接呈现原题或结合材料改写。项目题基于真实材料生成，保存其对应项目和引用字段，不自动套知识题要点。假设场景设计题不在首版。

### 2.2 配置与选题

- 首版岗位画像为 `ai_app_engineer.tech`，级别为初级；题目难度可用基础/应用两个层次，界面不提供尚未校准的 senior 级别。
- 默认 5 题。为保留旧版已有的题数配置需求，工程契约支持 5 或 8 题；5 题为知识 3、项目 2，8 题为知识 5、项目 3；知识专项全为知识题。8 题属于同一规则的扩展配置，首个闭环优先验证 5 题。
- 用户从已开放的 `agent/rag/backend` 选 1–3 个方向，默认全选；不沿用旧版必选 3–5 个维度。首版方向等权，按候选覆盖分配并记录实际覆盖；不提供尚无闭环定义的自定义评分权重。
- 主问题不在规划页提前展示。规划项保存考察点、方向、难度、题型与拟评估维度；开始后冻结计划版本。
- 同一场不重复题目 ID 或同一考察点的近义主问题。可从同一项目问不同切入点，但不得反复要求同一段项目介绍。
- 项目材料不足以支撑多道不重复项目题时，减少项目题并用审核知识题补足，开始前说明；不要硬凑项目数量。无项目时必须明确知识专项。
- 没有符合方向/难度的审核题时，在规划阶段提示调整方向/难度；运行时出现不可用则记录题目生成失败，不以无依据知识题或 STAR 评分补位。

### 2.3 生成与质量检查

按“候选题 → 检查 → 保存正式题面 → 展示”执行。默认一题只围绕一个主要问题，可附必要背景，不设不适合具体技术问题的极短字数硬门槛；长度上限作为可测的配置参数。

改写约束：考察点与适用评分维度不变、原要点仍适用、不能添加用户未陈述的项目事实、不能无端增加子问题。检查失败直接回原题；检查结果与降级原因保存。原题不需要为“用了模型”而再调用一次模型润色。

项目题保存 `project_ref` 和出题依据。校验引用指向已确认字段；模型判断语义关联性，代码检查字段存在和引用位置。材料无法支撑时换切入点或改为知识题，并显示实际覆盖，不把模型质量判断当成绝对正确。

冻结的计划记录原定目标；实际题型、方向、生成方式与适用评分依据另存在 turn 的正式快照。若降级改变题型，先更新实际快照再展示，评分与报告按实际题型处理，并记录与计划的差异；不得用项目题 rubric 评价替补的知识题。模型不可用导致项目题生成失败时按 03 的降级表收尾，不额外发起无上限的替补生成。

评分依据在正式题面保存时冻结。需要技术依据的项目评价可在已有审核知识材料中查找相关来源；没有足够依据时明确不确定，不在线临时抓取未经核对的信息进行确定性判错。

## 3. 回答与追问

### 3.1 轮次定义

一道主问题对应一个 `turn`；主问答为 `round_no=0`，追问为 1、2。`probe_count` 等于已经正式展示的追问数量，失败或被丢弃的草稿不计数。同一轮只能接受一次答案，提交后不可覆盖。

追问判断输入：已确认的相关项目信息、正式主问题、完整本题问答历史、审核要点或项目考察目标、已问列表。模型输出结构化建议：`should_probe`、`purpose`、`reason`、`evidence_refs`、`probe_question`。

`purpose` 仅允许 `clarify`（澄清）、`deepen`（深挖依据）、`check_consistency`（核对矛盾或边界）。`reason` 与证据供报告/排查使用，不在面试过程中直接泄露评分要点。

### 3.2 决策顺序

1. 若已终止、当前轮不匹配或已有处理中的请求，按接口契约拒绝或返回原操作。
2. 保存本轮回答。空白输入返回字段错误，用户可以选择跳过；“不会/不知道”是有效回答，不属于系统故障。
3. 已展示两轮追问、预算不允许或用户选择结束时，不再调用追问模型。
4. 模型建议追问时，代码检查 JSON、目的、引用、轮次、是否重复和是否直接泄露参考答案；语义检查的效果要通过样本验证。
5. 合格则保存追问并展示；建议不追问或校验/调用最终失败，则收尾本题。失败原因与“回答已经充分”必须区分。

字数和关键词可用作输入长度约束或诊断信息，不能代替语义充分性判断。短而准确可以通过，长而空洞仍可追问。项目题没有固定 `answer_points`，按项目考察目标评价，不走“要点为空所以一直追问”的逻辑。

## 4. 评分规则

### 4.1 两类评分

| 任务 | 维度键 | 评价内容 |
|---|---|---|
| 知识 | `correctness` | 技术判断是否正确，允许有依据的替代答案 |
| 知识 | `depth` | 是否解释原理、适用条件、取舍与边界 |
| 知识 | `structure` | 是否清晰地组织回答 |
| 知识 | `relevance` | 是否回应当前问题和考察目标；不依据学历或履历光环 |
| 项目 | `technical_reasoning` | 技术合理性、选型理由与取舍 |
| 项目 | `implementation_ownership` | 做法是否具体、个人贡献是否清楚 |
| 项目 | `validation_evidence` | 如何验证结果，证据与测量方法是否合理 |
| 项目 | `communication` | 表达是否清晰、是否回应问题 |

STAR 仅辅助组织材料，不要求每个窄问题都复述完整 S/T/A/R。验证证据不只接受业务数字：测试、日志、失败案例、前后对照、观察方法都可以。没有数字不自动扣固定分。

### 4.2 评分尺度与适用性

为使首版契约可实现，采用以下初始工程尺度，具体锚点例子在调试集校准并版本化：每个适用维度取整数 0–4。

| 分值 | 通用锚点 |
|---|---|
| 0 | 对已明确考察的内容无法提供有效回答，或存在关键错误 |
| 1 | 只有零散表述，明显缺少必要解释或依据 |
| 2 | 基本回应且主要内容成立，但解释与证据有限 |
| 3 | 回应清楚，有具体实施/原理/验证依据，符合该题要求 |
| 4 | 在该题范围内还能清楚解释权衡、边界或反例，证据充分 |

正式出题时冻结 `applicable_dimensions` 与问题目标，至少包含一个内容维度。追问可在同一目标内增加明确考察的维度，必须在提问前记录，不能评分时看用户哪里差才临时加考。

区分三个概念：

- **未考察**：该题与实际追问没有提供回答机会，维度标 N/A，不进分母。
- **已考察但回答不足**：可以低分；例如已经问“如何验证”，只回答“感觉不错”。
- **外部真实性未知**：无法核验业务数字或项目真实性，标 `unverified_claim`；评价讲解中的证据与方法，不能据此断言造假或全部视为 N/A。

模型输出各维度分、理由与引用；代码计算单题归一化分：

```text
item_score = round(100 × Σ适用维度分 / (4 × 适用维度数), 1)
```

首版适用维度等权，不额外叠加旧版 STAR 的 -5/-15 扣分。没有适用内容维度或输出无效时为评分失败，不制造分数。分数是版本化 rubric 下的练习摘要，不是通过率。

### 4.3 输入、证据和稳定性

评分使用本题全部已提交问答，生成一套最终评分并展示追问次数，不额外生成初答分，不按次数机械扣分。主动结束造成未回答的追问不作为用户“答错”；只评实际提交内容可支持的部分，并标中断。

输入包含正式问题、考察点、适用维度、回答历史、审核知识要点/相关技术依据、所需 JD 上下文。项目履历只提供背景，不替用户回答。不同模型、参数、Prompt、rubric、题库版本要记录，低 temperature 不等于可复现保证。

证据使用 `exchange_id + quote + start/end` 定位。引用先检查确实来自该轮用户答案；空证据必须有明确原因，如用户明确回答“不知道”。不能引用模型追问中的提示作为用户已掌握知识的证据。技术判错与不确定性分别标记，有来源的错误结论关联 `source_ref`。

非法分值、伪造引用、缺少必要维度时，本次评分结果不接受；在统一重试额度内修复一次，仍失败转待补评。不能通过向下取整或默认 40 分掩盖模型失败。

## 5. 报告与练习反馈

### 5.1 数字含义

分别展示 `knowledge_score` 与 `project_score`，各为有效单题归一化分的算术平均，保留一位小数。附该类有效题数与实际评估维度覆盖。没有该类有效分时为 `null`，显示“未评估/暂无有效评分”，不显示 0，不合成 `overall`。

每维度均值只聚合实际被评估的维度，显示有效样本数；不能把不同分母的样本假装等价。首版不做跨场能力趋势推断。

显示以下互不混淆的计数：计划题数、展示题数、有已提交答案的题数、有效评分题数、跳过题数、系统失败题数。已提交答案但随后跳过的题可出现在“有答案”计数中，但不在有效评分分母。

### 5.2 报告布局

1. 完成情况：结束原因、覆盖、有效题数；提前结束或有评分缺失时显著标注。
2. 知识表现与项目表现：有数据的类别显示分数与维度，无数据明确说明。
3. 逐题回顾：正式问题、问答、追问次数、评分证据、缺口、引用来源与不确定项。
4. 优先改进：通常两三项，有证据才给，不强凑；每项关联题目/回答，描述具体动作与自查方法。
5. 再练一次与导出。下一次建议可指出关注的知识点，不承诺能预测分数增长。

例：“你说‘感觉召回更准’，但没有解释样本与指标。下次补充一组固定查询、标注相关材料，说明比较前后使用相同的指标。”

语气直白、具体、尊重事实。禁止“可直接二面”“不建议投递”、伪造同岗人群均值或学习时长预测。技术证据不足时明确说明，不以招聘权威口吻包装。

### 5.3 报告状态与补评

报告状态独立于面试是否结束：`pending/ready/template_only/failed`。`is_partial` 表示提前结束或存在跳过/未回答/系统失败/缺评分；正常走完但跳过题目也要明确覆盖不足。

生成报告模型失败时，仍可用确定性模板展示已有问答与评分；没有任何有效评分时只展示会话摘要。报告算术、计数与来源由代码生成，模型只写有依据的文字，不允许模型重新算分。

用户主动补评只处理待评分失败项，不能改变已提交答案或悄悄覆盖成功评分。重试仍受会话硬预算；预算耗尽时拒绝新调用。补评成功生成新的报告修订号，保留旧修订快照并提示变化；同一请求重复到达不增加修订号。

## 6. 跳过、离开与结束

| 事件 | 业务处理 | 报告处理 |
|---|---|---|
| 离开页面 | 已接受操作最多继续至下一处等待；保留已提交进度 | 不主动生成结场报告 |
| 跳过当前题 | 已有回答保留，整题不记能力分；转下一题 | 标跳过，不作为能力 0 |
| 用户主动结束 | 先停止流程推进；保留已提交回答，对可评估未评分题尝试收尾 | 部分报告；评分失败保留待补评 |
| 全部计划项已收尾 | 正常结束；收尾包含回答完成、跳过、生成失败等 | 根据有效覆盖生成报告或摘要 |
| 软预算不足 | 减少后续追问，保留收尾额度 | 标记实际降级 |
| 硬预算不足 | 不再调用模型；保存已提交答案、结束并汇总已有结果 | 不为未评分题造分 |
| 单操作超时 | 有限重试/对应降级，或标记待恢复 | 说明系统原因 |

结束判断是“全部计划项已收尾”，不是“已评分数等于计划数”。一次中止不会因报告失败而撤销；重复中止返回同一结束记录。具体并发、迟到结果和恢复见 [03](03-系统架构与运行机制.md)。

## 7. Prompt 责任清单

| 模板 | 职责 | 输出与兜底 |
|---|---|---|
| `extract_profile` | 从材料定位必要字段，不编造经历 | 画像候选与出处；失败回人工编辑 |
| `recommend_topics` | 根据 JD 推荐已支持方向 | 枚举方向与理由；失败显示全部已支持方向供用户选 |
| `plan` | 建议考察点与项目切入点 | 代码验证配比/覆盖/材料；失败用受控模板分配 |
| `rewrite_question` | 个性化知识题题干 | 失败回审核原题 |
| `check_question` | 语义关联、考察点不漂移检查 | 不通过回原题/换项目切入点，受统一额度约束 |
| `ask_project` | 根据确认材料问一个真实项目问题 | 失败按正式降级记录收尾，不虚构问题 |
| `probe` | 根据历史给出有依据的追问建议 | 无效或失败后收尾本题 |
| `score_knowledge` / `score_project` | 按各自 rubric 输出证据与分值 | 无效则有限重试、待补评 |
| `report_narrative` | 根据已算好的结构化结果给建议 | 失败用模板 |

模板以文件和内容哈希版本化；插槽只填一次，用户文本不能被当成二次模板执行。详细措辞在样本实验中完善，不以一份未经测试的长 Prompt 代替验收。
