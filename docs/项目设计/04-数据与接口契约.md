# 04 · 数据与接口契约

> v2.0 · 目标契约。配套 [02 业务规则](02-面试业务规则.md)、[03 执行机制](03-系统架构与运行机制.md)。本文件不是已执行的数据库迁移。

## 1. 通用约定与状态

- ID 由服务端生成，不从文件名或用户内容生成；FAISS 使用受控整数映射。
- 时间按 UTC 保存、带时区序列化，页面按用户时区显示。统计耗时用单调时钟；跨重启操作保留起止时间和尝试记录。
- JSON 输入由 Pydantic 校验，数据库也设置必要的 NOT NULL、CHECK、FK 与 UNIQUE，不能只靠前端。
- 业务连接启用外键；配置 WAL 与合理 busy timeout，写事务保持短小。WAL 不意味着允许无限并发写。

### 1.1 会话与操作分离

| 对象 | 状态 | 含义 |
|---|---|---|
| `session.phase` | `PLANNING` | 材料已确认，计划待开始 |
| 同上 | `ACTIVE` | 已开始，可准备题目/等待回答/处理回答；细节看操作和 turn |
| 同上 | `FINISHED` | 不可再回答或出题，允许收尾、报告、待失败项补评与删除 |
| `operation.status` | `queued/running/recovery_required/succeeded/failed/cancelled` | 命令执行状态，独立于会话业务阶段 |
| `plan_item.status` | `pending/active/closed` | 计划位置状态 |
| `turn.state` | `generating/awaiting_answer/processing/closed` | 本题运行情况；generating 期间不接收答案 |
| `evaluation.status` | `pending/ready/failed` | 评分处理状态，跳过题无需创建评分 |
| `report.status` | `pending/ready/template_only/failed` | 报告展示状态，与会话结束独立 |
| `session.delete_state` | `none/deleting` | 删除中不再接受读取正文或新增业务 |

确认前 `draft` 只在临时缓存中，不建 SETUP 会话。旧版 `ASKING/PROBING/SCORING/REPORT/DONE/ABORTED` 不作为新表另一套同时维护的状态；其行为已映射到上表，避免冗余状态互相漂移。

`end_reason`：`completed/user_cancel/too_hard/no_time/budget_exhausted/system_failure`。用户中止理由仅限 `user_cancel/too_hard/no_time`；`completed` 与系统原因由服务端生成。

`plan_item.outcome`：`answered/skipped/unanswered/generation_failed`，仅 closed 时非空。有效评分数量单独计算，不把 `answered` 与评分成功等同。

### 1.2 合法动作摘要

| 当前状态 | 动作 | 成功后的稳定结果 |
|---|---|---|
| 无正式会话 | 确认草稿 | PLANNING，已确认材料保存 |
| PLANNING | 修改配置/重建计划 | PLANNING，新计划版本；题面不外露 |
| PLANNING | start | ACTIVE，准备首题的 operation 已登记 |
| ACTIVE + awaiting_answer | answer | 答案落库，turn processing；随后追问或收尾 |
| ACTIVE + 当前题存在 | skip | 本题 closed/skipped，准备下一题或结束 |
| PLANNING / ACTIVE | abort | FINISHED，阻止旧操作推进；独立 finalize |
| PLANNING / ACTIVE / FINISHED + 待恢复操作 | resume | 同一业务操作恢复，受 epoch 与阶段白名单约束；FINISHED 只能恢复收尾/报告等终态允许操作 |
| FINISHED | retry evaluation/report | 只处理允许的失败项，成功后新报告修订 |
| FINISHED | delete | deleting → 全部清理完成后资源不存在 |

没有 current turn 时 skip 返回 409；生成中存在本题时可以跳过并使旧生成结果失效。重复命令先查幂等记录，不因为当前状态已变就误报失败。

## 2. 业务数据结构

字段清单包含首版所需关键约束；具体 SQLAlchemy 声明和迁移文件按此实现。JSON 适用于有界明细，核心关系与唯一性使用数据库字段。

| 表 | 关键字段 | 约束/说明 |
|---|---|---|
| `schema_migration` | version, checksum, applied_at | version 主键；脚本已执行后不可改内容 |
| `interview_session` | id, owner_id, phase, delete_state, end_reason, revision, control_epoch, profile_id, level, mode, question_count, selected_dimensions_json, input_mode, jd_text, resume_profile_json, consent_version, provider_id, policy_snapshot_json, created_at, ended_at | owner_id 首版固定 local；题数 5/8；方向属于开放集；材料创建后冻结，变化需新建会话 |
| `plan_item` | id, session_id, seq, plan_version, task_type, dimension, difficulty, topic, generation_method, question_id?, project_ref?, form_reason?, scoring_targets_json, status, outcome? | FK session/question；UNIQUE(session_id, seq)；计划开始前可替换未开始版本，开始后冻结 |
| `turn` | id, session_id, plan_item_id, task_type, dimension, generation_method, fallback_reason?, state, probe_count, question_snapshot_json, source_snapshot_json, rubric_snapshot_json, interrupted, created_at, closed_at | FK session/plan；UNIQUE(plan_item_id)；复合外键/约束保证 plan 属于同一 session；probe_count 0–2；题型等表示实际出题，与原计划差异显式记录 |
| `exchange` | id, turn_id, round_no, question_text, purpose?, reason_json?, answer_text?, answer_mode?, answered_at? | FK turn；UNIQUE(turn_id, round_no)；轮次 0–2；只在正式题面校验成功后插入；答案只接受一次 |
| `evaluation` | id, turn_id, status, assessment_json?, item_score?, error_code?, model_context_json, created_at, updated_at | FK turn；UNIQUE(turn_id)；ready 才有有效分；成功后不覆盖重评；failed 可显式补评 |
| `report_revision` | id, session_id, revision_no, status, is_partial, counts_json, knowledge_score?, project_score?, dimension_summary_json, evaluation_snapshot_json, improvements_json, markdown?, model_context_json, created_at | FK session；UNIQUE(session_id, revision_no)；不含 overall；快照不可被后续题库/补评静默改变 |
| `operation` | id, session_id, owner_id, kind, idempotency_key, request_hash, expected_epoch, retry_of_operation_id?, status, safe_request_json, result_refs_json?, error_code?, created_at, updated_at | FK session；重试关联本会话失败操作；UNIQUE(owner_id, kind, idempotency_key)；同场最多一个 queued/running/recovery_required 的活跃修改操作，用部分唯一索引和事务保证 |
| `operation_step` | id, operation_id, step_key, status, result_json?, attempts, version_context_json | FK operation；UNIQUE(operation_id, step_key)；保存恢复所需结果，归属会话敏感业务数据 |
| `call_attempt` | id, operation_step_id?, draft_scope_id?, session_id?, role, attempt_no, status, reserved_tokens, actual_tokens?, reserved_cost, actual_cost?, currency, pricing_snapshot_json, provider_request_id?, started_at, ended_at | FK step/session（允许预览无 session）；同 scope/step/attempt 唯一；失败/未知也记账；不存 Prompt 或模型正文 |
| `budget_account` | id, scope_type, scope_id, spent, reserved, hard_limit, currency, updated_at | 会话与全局试测账本；原子预留；全局累计不因删会话而归零，不含用户正文 |
| `question` | id, stable_faiss_id, revision, dimension, difficulty, content, objective, answer_points_json, acceptable_alternatives_json, common_errors_json, applicable_dimensions_json, tags_json, status, source_refs_json, checked_at, content_hash | faiss ID 唯一稳定；status=draft/verified/retired；只有 verified 可选；已用题靠 turn 快照保留历史 |
| `knowledge_source` | id, title, locator, source_type, source_version?, reviewed_excerpt?, checked_at | locator 为真实 URL 或仓库路径；保存必要片段与出处，不强制复制全部外部文章 |
| `deletion_job` | id, target_session_id, status, steps_json, safe_error_code?, created_at, updated_at | target_session_id 不设删除后失效的 FK；仅不透明 ID 与清理状态，不保存正文 |

M1 第一批的公共题库使用独立 SQLite 文件。种子文件用 `source_refs` 表示出处 ID，数据库通过 `question_source` 保存有顺序的外键关联，查询返回该题的完整出处。`001_question_bank.sql` 负责首次初始化，导入和查询均核对结构版本与迁移校验值。会话、用户数据及后续升级流程见本文件的目标契约。

`owner_id` 只是未来访问检查的边界，固定 local 不等于已经有多用户鉴权。每个 repository 方法都按访问者和资源范围查询，为以后增加身份系统保留单一入口。

建表顺序按 FK 父子依赖安排。删除按子到父在业务库事务完成；显式删除或级联属于实现选择，但必须有确定的依赖清单和测试，不能把“禁用 CASCADE”当安全保证。

### 2.1 画像契约

```json
{
  "candidate": {"display_name":"候选人","years":null,"education":null,"skills":["Python"]},
  "projects": [{
    "id":"p_1","name":"课程检索练习","action":"实现了分块和检索",
    "background":null,"result":null,"excerpt":"使用固定查询比较了两种分块大小",
    "field_provenance":{"action":{"origin":"extracted","verification":"exact","source_ref":"paragraph_3"}}
  }]
}
```

确认后仅保存上述必要字段、来源标记及定位标识，不保留整份原文和未确认候选正文。临时来源片段可供确认页面显示，过期清理。用户改动字段时改为 edited，不伪称原文摘录。

M1 第三批以 `001_init.sql` 初始化独立业务库 `data/interviews.db`。人工填写确认时，在同一事务中写入 `PLANNING` 会话、确认材料与幂等标识。当前 CLI 识别 `text`、`form` 两种入口。人工来源标记为 `provided` 或 `edited`，缺失字段标 `missing`。本地处理的 `provider_id` 和 `consent_version` 留空，配置使用初级、5 题、全方向的默认值。模型提取来源、Web 草稿缓存和后续业务表按目标契约分阶段建设。

### 2.2 评分契约

```json
{
  "task_type":"project",
  "rubric_version":"project-v1",
  "dimensions":{
    "technical_reasoning":{
      "applicable":true,"value":3,"reason":"解释了选型约束",
      "evidence":[{"exchange_id":"x_1","quote":"需要本机运行","start":0,"end":6}],
      "source_refs":[]
    },
    "validation_evidence":{"applicable":false,"value":null,"reason":"本题未考察","evidence":[],"source_refs":[]}
  },
  "uncertainties":[{"type":"unverified_claim","message":"业务规模由用户陈述，未外部核验"}],
  "comment":"此处为结构示意，不是实测评分。",
  "improvements":[]
}
```

落库的评分结构包含该 `task_type` 的全部维度键。`applicable` 以本题已冻结的评分目标为准，`value` 为 0–4 整数或 N/A 的 `null`。引用的起止位置由服务端在原回答中定位。上例仅展示字段形态。

实验模式的单题评分请求 `interview-json-v4` 使用较小的模型输出结构。模型只填 `dimensions` 中冻结的适用项。每项包含 `value`、`reason`、`evidence`，可附缺证说明和来源 ID，顶层可附 `uncertainties`。程序检查适用项是否齐全，按题目快照补齐题型、评分版本和 N/A 项，再校验分值、证据与来源。评分失败可在现有预算内有限重试。

`item_score`、分类均分和统计由代码计算，模型无权提供 authoritative total。版本上下文包含模型标识、请求参数、Prompt 内容 hash、rubric 与题库版本；允许模型别名时记录供应商返回的版本/指纹（若提供），不虚构精确版本。

M1 第四批实现评分校验与聚合模块。适用维度缺少引用时，使用 `evidence_absence_reason` 记录缺证原因。引用以当前题已提交答案为范围重新定位，`start` 含起点、`end` 不含终点，按 Python 字符索引计算。同一答案内重复出现的原文片段取首次位置。单题与均分用精确分数执行 `round(…, 1)`，恰好在中点时取最近的偶数末位。维度均分沿用 0–4 分尺度，并返回有效维度样本数。正式评分落库和报告修订按后续流程接入。

## 3. 接口与响应

统一 `/api/v1`；JSON 时间使用 ISO8601。成功响应携带当前 revision 和 operation，异常响应保留 trace_id/request_id，但不得泄露密钥或原始模型请求。

```json
{"ok":true,"data":{"operation_id":"op_1","status":"queued","revision":8},"error":null,"trace_id":"tr_1"}
```

```json
{"ok":false,"data":{"current_revision":9},"error":{"code":"STALE_REVISION","message":"页面进度已更新，请刷新后继续","retryable":false},"trace_id":"tr_2"}
```

所有修改会话的请求需要 Idempotency-Key；同 key 同 body 查询原结果，body 用规范化 hash 比较。请求 key 和正文不记录到普通日志。同键命令未完成返回同一 operation；不同键的并发修改返回 409，跳过/中止/删除按明确的取消规则处理。前端不能把 202 当完成。

### 3.1 材料与会话

M3 在 `/api/v1` 下挂载本机业务接口。示例与带标签的文本使用进程内预览，确认回执由已有业务库持久化。配置复用规划校验；接收首题、回答、跳题、下一题和结束请求时先登记操作，响应后处理。刷新用只读状态接口，等待后仍未完成可显式继续。报告缺失时允许显式生成。正在删除的会话正文统一按不可访问返回 404，清理状态由删除任务接口单独提供。

| 方法与路径 | 输入 | 输出/约束 |
|---|---|---|
| POST `/drafts/preview` | JSON 文本/示例/表单，或 multipart 文件；input_mode、provider_id、consent_version | 画像候选、字段提示、draft_id、expires_at；无长期正文；相同未过期 key 复用缓存，重启/过期提示重新提交 |
| POST `/sessions` | draft_id、确认画像、JD、profile、题数、选项 | 201 session_id/revision；检查同一 draft 只创建一个会话；先查询幂等结果再检查草稿是否过期 |
| GET `/sessions` | limit、cursor、status | 仅列表摘要、阶段、进度、两类分数/有效题数；不返回画像正文，不含 overall |
| GET `/sessions/{id}/state` | — | 完整恢复视图，见下；允许读取当前操作与正式题面，不泄露待问题面 |
| PATCH `/sessions/{id}/config` | expected_revision、方向、难度、题数 | 仅 PLANNING，登记重建计划操作，202；废弃旧计划草稿 |
| GET `/sessions/{id}/plan` | — | 考察方向、难度、题型数量与覆盖提示；无具体题面或答案 |
| POST `/sessions/{id}/start` | expected_revision | 202，登记首题准备；首题由 start 负责，不再同时保留另一个会重复生成的 /next 命令 |
| POST `/sessions/{id}/clone` | — | 创建新 PLANNING 会话，复制确认材料与配置，不复制答案或分数 |
| POST `/sessions/{id}/abort` | expected_revision、reason | 终止记录立即提交，202 finalize 操作；重复同键返回相同记录，已终止的新中止请求返回已有结束结果 |
| POST `/sessions/{id}/resume` | expected_revision、operation_id | 仅待恢复的有效操作；202；不允许重新打开已结束面试 |
| DELETE `/sessions/{id}` | expected_revision（存在时） | 活跃会话 409，需先结束；清理中 202 + deletion_job；全部完成或不存在 204 |

首次确认创建会话与创建幂等 operation 在同一事务完成。`draft_id` 临时缓存同时标记已创建 session_id；缓存失效时仍可用命令幂等记录取回已创建会话，不需要再次上传才能确认创建成功。

M4 材料上传使用 `POST /api/v1/drafts/document?format=pdf|docx`，请求头含 `Idempotency-Key` 和 `Content-Type: application/octet-stream`，请求体为文件字节。响应沿用 30 分钟草稿并附遮盖常见联系方式的 `source_text`，只供该次核对，不写数据库。确认仍走 `POST /api/v1/sessions`，持久化确认字段与来源类别。手填从 `/drafts/preview` 的 `source=form` 建立空草稿。

单文件最多 5 MiB，PDF 最多 20 页，提取文本最多 16000 字符，DOCX 正文 XML 最多 2 MiB。文件超限返回 413 `DOCUMENT_TOO_LARGE`。页数、展开大小、空文本、加密和文件无效分别返回 422 安全提示，引导分段、重新导出或粘贴文本。PDF 双栏及复杂排版需要人工确认，DOCX 读取正文与表格中的文字段落。

M5 的 `POST /api/v1/sessions` 增加可选布尔 `cloud_assistance`，默认 false。仅实验模式已配置且材料不是固定示例时可提交 true。确认后冻结为单场选择；「再练一次」使用新会话并回到本机模式。旧会话按本机模式读取。云端追问/评分失败使用原有错误码和缺分语义，网页证据仍只从已提交回答定位。

### 3.2 回答、评分与报告

单题评分未通过输出校验时，报告仍保留已提交问答，评分为空。新会话的失败结果可在 `evaluation.model_context.validation_failure` 中附带 `stage`、`reason`、`field` 与固定文案。字段路径只使用应用已知字段，未知字段显示为 `*`。失败的模型正文、原引用和校验入参不随诊断持久化。历史报告可能只有原来的 `OUTPUT_INVALID`。

| 方法与路径 | 输入 | 输出/约束 |
|---|---|---|
| POST `/turns/{id}/answer` | exchange_id、expected_revision、answer、answer_mode=text | 202，答案持久化成功后处理；失败 5xx 不称已保存；下一追问/题由操作推进 |
| POST `/turns/{id}/skip` | expected_revision | 202，本题关闭、取消旧结果提交资格；已关闭题不再修改 |
| GET `/operations/{id}` | — | 状态、结果引用、安全错误；同访问者范围，不返回内部 Prompt |
| GET `/sessions/{id}/report` | revision 可选 | FINISHED 后可读；生成中返回状态；不存在评分时返回摘要；不以“没有分数”误判 500 |
| POST `/turns/{id}/evaluation/retry` | expected_revision | FINISHED 且评分 failed/待生成；仍受冻结版本与预算约束；成功创建报告修订 |
| POST `/sessions/{id}/report/retry` | expected_revision | 仅 failed/template_only 状态尝试模型叙述；已有有效评分不重评；无预算则保留模板 |
| GET `/reports/{id}/export` | — | 下载当前指定修订 Markdown，直接响应不留额外服务器导出副本 |
| GET `/deletions/{job_id}` | — | 删除状态和安全失败原因，不返回已删除正文 |

面试结束前不提供普通用户可读的评分/标准答案接口；内部评分可提前完成但集中反馈到结束时。观察台也不暴露正文以绕过反馈时机。

首版 GET 只读已有数据，不隐式调用付费模型或推进状态。方向推荐可在创建/修改配置的 operation 中完成。所有真实模型调用由明确的创建/修改/继续操作触发。

M2 第一批通过 CLI 同步运行确定性规划。`002_interview_plan.sql` 增加计划版本、难度、计划项与操作记录。计划通过独立题库中的题目 ID 和修订号定位审核条目，正式展示前需要重新核对审核状态与修订。项目项引用同一会话已经确认的项目 ID 与字段。配置、计划项与无正文操作回执一起提交。重试相同命令取原回执，读取计划取最新版本。

M2 第二批通过 `003_first_question.sql` 增加 `turn`、`exchange` 和 `operation_step`。本地 `start` 接受事务冻结当前计划并登记 `queued` 操作，提交后由 CLI 调用 LangGraph 节点。发布事务保存正式题面、来源与 rubric，并以操作步骤的 ID 回执防重。`resume-start` 显式继续已登记的开始操作。

M2 第三批 CLI `answer` 复用 `exchange` 一轮一行的约束，按 `answer_text IS NULL` 写一次。答案、UTC 提交时间、题目 `processing` 状态、会话修订和控制代次、`queued` 操作在同一事务提交。重复请求返回原接收回执。CLI `state` 从会话范围内读回当前已发布题面和已保存答案，命令记录只含 ID、状态和请求指纹。

M2 第四批 `process-answer` 执行同一业务图的追问决策节点。已校验追问写入下一轮 `exchange`，题目回到 `awaiting_answer`，该决定随 `operation_step` 一次提交。提议不追、到达上限或输出失败时保留已答内容，回执记录 `decision=score_pending` 和对应原因码。`state` 只展示公开决策与当前题面，证据和理由留在业务库。

M2 第五批 `score-answer` 从 `score_pending` 登记单题评分，`004_evaluation.sql` 保证一题一条评分记录。节点按全部已提交问答、冻结维度和出处校验样例，代码计算 `item_score`。评分成功和失败都收尾已答题，失败的评估分数为 `null`。评分、题目收尾与操作回执同事务提交，普通进度只展示评分状态。`resume-score` 可继续已登记操作。真实模型调用、报告和持久化图 checkpoint 在后续接入。

M2 第六批的本地 `advance` 在当前题已收尾且会话无活跃操作时接受，按冻结计划的 `seq` 选择最早的挂起项。首题仍由 `start` 负责。已展示题与考察点避免再次使用，同次推进中无法出题的项记录 `generation_failed`，原因和发布结果共用事务回执。所有计划项闭合后设置 `FINISHED` 和 `completed`。`state.progress` 分别统计计划、收尾、已答、有效评分、跳过与失败数，`current.seq` 为当前计划位。

M2 第七批用 `005_report_revision.sql` 保存报告修订。`generate-report <session_id>` 只对已结束且可访问的会话生成初版模板，短事务内保存快照，并发或重放复用已保存的报告。`report <session_id> [--revision N]` 只读。首次生成前返回 `pending`，指定不存在的修订返回 `RESOURCE_NOT_FOUND`。模板使用 `status=template_only`，无有效分时为 `kind=summary`，两类分数均为 `null`。逐题快照含已发布问答、实际题型、评分证据、冻结来源及已记录的失败原因；六项覆盖计数与 `state.progress` 各自按其契约返回。模型叙述、补评产生的新修订与 Markdown 导出待对应阶段接入。

M2 第八批 CLI `abort <session_id> --expected-revision N --key KEY --reason REASON` 在一个事务内登记结束、增加控制代次、取消原活跃操作、标记中断题并登记 `finalize`。已经收尾的题维持原结果，未回答的计划项记 `unanswered`。收尾节点只尝试评分有提交的中断题。未提供本地评分样例时，保留已提交内容并记 `MODEL_UNAVAILABLE`，没有有效分时生成会话摘要。评分结果、收尾回执先提交，再独立保存部分报告。`resume-finalize <session_id> <operation_id>` 可继续已登记操作，或在报告未写入时重试保存。重复中止复用原结束记录，报告失败不撤销会话 `FINISHED`。

M2 第九批 CLI `skip <session_id> <turn_id> --expected-revision N --key KEY` 以整题为单位。会话内当前题标记 `closed/skipped`，保留正式问答，取消活跃追问或评分，并清除尚无结果的评分占位。上述操作与 `skip` 排队回执、控制代次在同一事务提交。后续复用 `advance_plan` 发布下一道或结场。用 `resume-skip` 继续已登记操作。`state.operation.skipped_seq` 在推进完成时返回跳过的计划位。报告统计已展示、已答和跳过，跳过题没有有效评分，也不计系统失败。最后一题跳过后按正常结场路径显式生成报告。

M2 第十批 CLI `resume <session_id> [--operation-id ID] [--expected-revision N]` 复用当前控制代次的已登记操作。只读 `state.resume` 返回 `{operation_id, kind, reason}` 或 `null`，其中 `queued` 表示已排队的业务步骤，`report_pending` 表示结束收尾已保存、仅剩报告。指定操作与当前记录不符或修订过期时刷新状态后再继续。等待用户输入和已完成步骤返回已有进度。`resume` 不接受新答案、不登记新操作；普通结场报告仍可显式生成。旧的按操作种类继续命令仍可用。

M2 第十一批 `006_session_budget.sql` 先实现会话级 `budget_account`，尝试通过 `operation_id + step_key + attempt_no` 定位。预留时步骤结果可能尚未写入，账本直接关联已登记的 operation。金额以十亿分之一美元的整数保存，预算配置在会话内冻结。调用前按无缓存估算预留，普通问答保留收尾额度，评分和报告可用完整剩余额度。结算使用同一价格快照和已知用量；`usage_unknown` 保留预留金额，补齐用量后幂等结算。最多两次尝试，调用方仍需按错误类型决定是否重试。本批未接入真实供应商、每题限制、全局预算和材料草稿账本。

## 4. 错误码与用户提示

新契约用语义错误码代替旧 E 编号；旧编号仅存在历史文档。不得让业务同时维护两套含义相反的映射。

| code | HTTP / 操作状态 | 提示与处理 |
|---|---|---|
| `INVALID_INPUT` | 422 | 标明具体字段，空回答可选跳过 |
| `DRAFT_EXPIRED` | 410 | 预览已过期，请重新提供材料 |
| `UNSUPPORTED_DOCUMENT` | 422 | 暂不支持此扫描件/图片，请粘贴文本 |
| `EXTRACTION_NEEDS_REVIEW` | 200 + 字段提示 | 部分字段无法定位，请核对或填写 |
| `SENSITIVE_CONTENT` | 422 | 指明疑似字段，请确认删除不必要的个人信息；不在日志回显命中值 |
| `IDEMPOTENCY_CONFLICT` | 409 | 同一请求标识对应不同内容，刷新后重试 |
| `STALE_REVISION` | 409 | 页面进度已更新，请刷新 |
| `OPERATION_IN_PROGRESS` | 409 或同键 202 | 当前操作处理中，返回可查询 operation |
| `ILLEGAL_ACTION` | 409 | 当前阶段不允许该操作，不回滚有效进度 |
| `RESOURCE_NOT_FOUND` | 404 | 记录不存在；DELETE 不存在例外为 204 |
| `CONFIGURATION_ERROR` | 503 / failed | 模型配置不可用，修正后再试；不自动重试 |
| `MODEL_UNAVAILABLE` | operation failed 或降级 | 临时模型故障，有限重试后说明实际降级 |
| `OUTPUT_INVALID` | operation failed 或降级 | 返回内容未通过校验，评分不计为零 |
| `QUESTION_UNAVAILABLE` | operation failed/题目失败 | 当前条件无合适审核题，调整规划或标记覆盖不足 |
| `BUDGET_EXHAUSTED` | 409 / 收尾 | 已达本次预算，保存现有回答并展示已有结果 |
| `STORAGE_ERROR` | 503 / failed | 本次内容未确认保存，请保留输入并重试；不声称成功 |
| `DELETE_ACTIVE_SESSION` | 409 | 请先结束本场面试 |
| `DELETION_IN_PROGRESS` | 409，正文读取 410 | 正在清理，稍后查看进度；不得继续读正文 |
| `DELETE_FAILED` | job failed | 部分清理未完成，可以重试，不声称已全部删除 |

操作已接收后失败通过 operation/state 表达，不把后台失败硬塞成已经返回的 HTTP 错误。retryable 指同一安全操作可否重试，不表示允许忽略预算或当前 revision。

## 5. 观测数据与版本

`observe.db` 与 `graph.db` 独立于业务库；不假设跨库 FK。trace/span 按会话/操作关联，仅保留安全元数据。2026-11-19 的 P0 修正使新 input/output 始终为空、历史读取隐藏正文，原始异常转安全错误码，见[问题记录](记录/问题记录.md)。历史数据库内容未物理清理，graph 存储仍待实现，不能将 P0 验证代替未来全部数据路径验证。

每次评测和正式评分关联版本包：`app_commit`（若已有提交）、`design_version`、`prompt_hashes`、`rubric_version`、`question_set_version`、`index_manifest_hash`、`model_id/params`、`parser_version`。没有 commit 时标 working-tree 并保存受测文件 hash，不编造提交号。

图 state、任务缓存和中断 payload 也必须经过正文泄露检查。业务快照用于解释旧结果，不能因清理原始上传而删除解释报告所需的已确认材料和问答。

## 6. 数据生命周期与删除

| 数据 | 默认保留 | 删除机制 |
|---|---|---|
| 原始上传/解析临时文件 | 完成预览请求后清理；异常残留启动扫描 | 应用专用临时目录，路径约束，读取期限受限 |
| 未确认文本、字段候选及预览对照 | 30 分钟缓存，重启可丢失 | 到期清理；确认后清理缓存；过期明确提示 |
| 已确认画像/JD/问答/评分/报告/业务步骤结果 | 用户手动删除 | 会话删除任务 |
| 会话 trace 及原始事件文件 | 可配置短期，默认 7 天 | 到期或单场删除；没有正文也执行对应清理 |
| 普通技术日志、未确认草稿用量元数据 | 默认 7 天 | 不记录正文或敏感值；到期清理，非业务恢复源 |
| checkpoint 与编排代次记录 | 会话存在期间 | 结束后可清理无用代次；单场删除清全部代次 |
| 应用内迁移备份 | 仅必要升级恢复期，默认 7 天 | 纳入备份清单；涉及会话删除时清掉可能含该会话的备份 |
| 公共审核题库与索引 | 长期维护 | 独立维护操作，不随单场删除 |
| 全局费用累计 | 当前试测预算周期 | 仅聚合计数，不因删会话重置，不含正文 |
| 用户下载导出副本 | 用户自行决定 | 应用无法保证删除外部复制件 |

### 6.1 删除流程

1. 仅允许结束后的会话删除；事务内设置 deleting、创建 deletion_job、取消有效操作并增加 epoch，正文接口立即不可用。
2. 停止该会话后续写入，排空或丢弃观测队列中该会话项；远端迟到响应只允许更新无正文全局费用聚合，不重建会话内容。
3. 逐步清理会话文件、trace/原始事件、全部图代次 checkpoint、应用管理备份。缺失视为完成，真实错误写入无正文清理进度供重试。
4. 业务库在一个事务中按关系删除 report/evaluation/exchange/turn/plan、operation_step/call_attempt/operation、会话账本与 session；全局费用聚合保留。
5. 应用管理的各副本与业务内容全部清理成功后，job 标完成，DELETE 才视为成功；用户下载或服务商留存的副本不在应用可控制范围。任何步骤失败，保持删除中/失败的可重试状态，不能恢复为正常可读会话。

文件与多个数据库不存在统一原子事务，因此采用有进度的幂等清理；先删某个文件成功不代表其余已成功。deletion_job 只保留不透明 ID 和步骤状态，不复制用户材料。

备份清单记录创建时间、schema 版本和所含会话 ID；若无法确定备份是否含目标会话，保守清理所有相关应用内备份，并说明这些备份不能再用于恢复。重新恢复备份必须校验清理记录，防止复活已删除会话。应用逻辑删除不宣称完成磁盘取证层面的安全擦除。

### 6.2 云端处理提示

在首次发送材料前展示所配置服务商、发送的数据类型和用途；确认说明后执行。后续显示当前处理方式，服务商变化重新提示。基础清理减少明显联系方式，但自由文本仍可能含个人信息；不能称“只在本机处理”。删除本机数据不代表能删除服务商可能保留的记录，不作超出控制范围的承诺。

## 7. 迁移与兼容

使用 `001_init.sql` 等编号脚本和 schema_migration，校验 checksum，不能编辑已应用脚本冒充新版本。初始化、升级、只读检查分开。已存在用户数据时先创建一致性备份再升级；SQLite WAL 模式下使用一致性备份机制或停服完成 checkpoint，不仅复制正在变化的单个 .db 文件。

可事务化的迁移在一个事务内执行，失败回滚并停止启动；不可事务化变更必须另写步骤与恢复说明。没有通用自动降级承诺；恢复备份也须遵守删除记录。业务库、observe 库和图存储的版本分别检查，不能把业务 schema_version 当所有组件都兼容的证明。

开发测试库只有在明确标记可丢弃时才可重建；真实练习数据不因“个人项目”自动被视为可丢弃。配置、日志、运行数据库、备份、真实材料和密钥均不提交仓库；测试 fixture 使用合成材料。
