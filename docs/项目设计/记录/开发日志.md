# 开发日志

> 本目录记录新版设计之后的实际工作。旧阶段见[原问题记录](../../问题记录.md)与[原交接](../../交接文档.md)。
> 本文件记录工作与学习进度；故障写[问题记录](问题记录.md)，效果对比写[实验记录](实验记录.md)。

## 1. 何时记录、记录到什么程度

- 每次有实质开发/设计/验证活动后补一条，最迟当天结束前；不要等项目结束凭记忆补故事。
- 每条用 5–10 分钟写清目标、实际变更、验证、理解情况和下一步，不抄整段聊天。
- 区分“AI 协助生成”“自己理解并修改”“独立排查”等参与方式。用了辅助工具不是问题，不能把未理解代码说成独立掌握。
- 写能定位的文件、测试名、命令、结果路径、提交号或实验 ID；没有运行就写未运行，没有测量就写未测量。
- 不记录 API key、真实简历、个人回答正文。证据用合成输入或脱敏片段，原始敏感数据留受控运行目录。

## 2. 日志模板

```markdown
### DEV-YYYYMMDD-NN · 本次工作的具体目标
- 类型：设计 / 实现 / 验证 / 学习 / 整理
- 对应里程碑、需求或问题：M? / R? / ISSUE-?
- 实际投入：如实填写；没记录就写未计时，不估造小时数
- 完成了什么：具体行为和文件
- 为什么这样做：需求、取舍或实际证据
- 怎样验证：命令/测试名、输入版本、结果或产物链接
- 未验证/未完成：具体限制
- 我能解释什么：用自己的话描述数据流或关键机制
- 还不能解释什么：要补的概念或代码
- 关联问题/实验：ID 或无
- 下一步：一项可执行、可验收的动作
```

## 4. 每个里程碑结束时的理解检查

用自己的话回答并链接到代码/证据，回答不清就记录为学习待办：

1. 这阶段解决哪个用户或工程问题？
2. 一次输入经过哪些模块，在哪里保存，哪个记录是权威？
3. 最容易失败的步骤是什么，已经实际验证过哪些故障？
4. 为什么采用当前方案，放弃了哪个方案，代价是什么？
5. 有哪些结果是测出来的，哪些仍是估计或假设？

这些回答可以逐步成为面试讲解素材，不需要提前写成宣传文案。
